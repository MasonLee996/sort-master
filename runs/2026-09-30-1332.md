# 第 99 轮 · 加管次数上限与记录（P0）

## 一、本轮做了什么

死局出口的「看广告加管」原先**没有任何次数限制**，记录也只出现在死局弹窗里那一次 —— 想加几根加几根，局面可以被无限刷成"能过但没意思"，步数基准和星级也随之失去意义。

| 项 | 内容 |
|---|---|
| 上限 | `const MAX_ADD_TUBES = 3;` 单关最多 3 次 |
| 记录 | `let addedTubes = 0;` 单关计数，**切关 / 切每日谜题归零**；HUD 新增常驻「加管 `0/3`」 |
| 死局弹窗 | 按钮文案随剩余次数变化：`看广告加管（剩 N 次）` → 达上限后 `加管次数已用完` 并**置灰禁用**；下方 `#deadAddInfo` 同步说明还剩几次 / 已达上限 |
| 同步出口 | 新增 `syncDeadAdBtn()`，切关、加管后、开弹窗都调它 —— 否则会出现"切关后按钮仍显示已用完"的脱节 |
| 评分口径 | 广告加管计入辅助操作：满星条件由 `!usedUndo && !usedHint` 改为 `!usedUndo && !usedHint && addedTubes===0` |
| 说明文案 | 胜利弹窗补一行「本关用了 N 次广告加管，属辅助操作，最高 ★★」；help 第 6 条星级规则与新增的「加管上限」条目同步更新 |

## 二、两道防线（顺序很重要）

```
btnDeadAd.onclick:
  ① 先判上限  → 达上限直接 toast 返回，【绝不进入广告流程】
  ② 再 hideDeadlock() / noAds 分支
  ③ showAd(cb) → cb 里 if(addTube()) 才提示成功
```

`addTube()` 自身也做一次 `if(addedTubes >= MAX_ADD_TUBES) return false;` 兜底（双保险：即便按钮的 `disabled` 因某种原因失效，也不会越界）。

**为什么顺序关键**：如果把上限判断放在广告回调里，玩家会先看完 15 秒广告、然后被告知"加不了" —— 这是明确的体验事故。用例专门覆盖了这条路径。

另外用 CSS `button.act[disabled]{opacity:.4;pointer-events:none;filter:grayscale(.3);}` 统一置灰样式，而不是在 JS 里手写 `style.opacity`。

## 三、⚠️ 本轮开工时发现的事故（必须记录）

动手前 `git diff` 发现：**工作区里已经存在同一任务的一份半成品**——

- `index.html` 中有**两行重复的 `const MAX_ADD_TUBES = 3;`** → 整个脚本 `SyntaxError`，**游戏实际处于白屏状态**（只剩 `window.onerror` 兜底画出的错误信息）；
- 同时也已加好了 `.act[disabled]` 样式和 HUD 的 `#hudAdd`；
- `verify.js` 里也已被追加了一整段同名用例（用的是 `addedTubes` / `MAX_ADD_TUBES` / `deadAddInfo` 命名）。

但它**既没有 commit，也没有写任何 memory / 日志**（推测是一次被中断的运行留下的）。

### 处置原则：不删别人的测试、不另起一套命名

1. **不删除**那段既有用例 —— 删掉跑不过的测试是最像作弊的举动；
2. 把自己的实现**对齐到它期望的接口**（`addedTubes` / `MAX_ADD_TUBES` / `deadAddInfo` / `hudAdd` / `syncDeadAdBtn`），因为那些命名和它已经写进 `index.html` 的半成品是一致的；
3. 把自己那份用例也改成同一套命名；
4. 修掉那个致命的重复 `const`；
5. 两段用例一起跑，全绿。

顺带做了一次设计收敛：原来我打算在画布顶部画一个「已加管 ×N / 3」角标，既然 HUD 已经有常驻记录，**画布角标删掉** —— 避免同一信息重复两处，也免去"顶部文字可能与左右侧栏/管身打架"的隐患。

**教训：动手前先 `git diff` 看清工作区真实状态，不要假设它就是上次提交的样子。**

## 四·补、发布阶段的两次事故

### A. 误把临时中间产物推上了公开仓库

`push.py` 的变更清单是"已跟踪改动 + **全部未跟踪文件**"，于是一个 `.tmp_check.js`（44KB，把游戏脚本单独抽出来做语法检查的中间文件，由那次被中断的运行留下）**被连带推到了公开仓库**。

处置：
1. 新增 `.workbuddy/tools/rm_remote.py`（走同一个连接器端点调 `delete_file`），删远端 `.tmp_check.js` → commit `515806c`；
2. 本地删除；
3. `.gitignore` 补 `*.tmp.js` / `.tmp*` / `*.bak` / `*.orig` / `*~`；
4. **给 `push.py` 加安全阀**：命中 `/^\.tmp|tmp_|_tmp|~\$|\.tmp\.js$|\.bak$|\.orig$|~$/` 的路径**一律跳过并大声打印**，而不是默默推上去。

### B. ⚠️ 推送之后，工作区的 `index.html` 被外部改动了

`git reset --mixed` 对齐后 `git status` 显示 `index.html` 仍有改动，内容是我刚加的 HUD 注释行被删掉。查看 mtime：`13:41:34` —— **晚于我这次 push**（约 13:41:0x），即**有另一个进程在我推送之后又写了这个文件**（而且当时读到的是半写状态：连续两次 `git diff` 的结果不一样）。

处置与结论：
- 先确认功能性代码是否受损（`addedTubes`/`MAX_ADD_TUBES`/`deadAddInfo`/`syncDeadAdBtn` 全在，只有一行注释被删）→ 重跑验证桩 **PASS=142 / FAIL=0**，功能未受损；
- 补回注释，记录 `sha256(index.html)`，**隔 20s 再算一次**确认哈希稳定（`1b84822003e000a7` 两次一致），排除"持续被改"；
- 重新对齐远端并核对**线上产物与本地逐字节一致（60,157 字节）**。

**这个工作区确实有两个执行者在写。** 证据链：① 开工时已有同一任务的半成品（含致命重复 `const`）；② `.tmp_check.js` 是"把脚本抽出来单独做语法检查"的中间产物，不是我创建的；③ push 之后文件被改写；④ 最后工作区里出现了一份**我从未写过的轮次文档 `runs/2026-09-30-1344.md`**，内容同样自述为"第 99 轮 · 加管次数上限/记录"，并在文中写明"与并行实例收敛后的版本一致"——**它知道我在。**

已排查：项目里只有**一个**自动化配置（`收纳大师 · 持续优化循环`，每小时一次），所以重叠更可能来自"定时触发"与"手动会话"撞在一起，而不是配置了两条重复自动化。建议：跑这类循环时避免在自动化即将触发的时间窗内再手动发起同一任务。

因此本轮把"开工先 `git diff`"和"交付后核对线上字节一致"都当成了必做步骤 —— 它们各自独立地救了一次场。这两条已写入 `.workbuddy/memory/MEMORY.md` 作为常驻工作流。

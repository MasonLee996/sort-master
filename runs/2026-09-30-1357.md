# 第 100 轮 · 生成耗时预算保护 + 自适应遮罩（P0）

## 一、先测，再改

这轮没有直接动手改代码，而是**先写基准脚本找真实数据**：新增 `.workbuddy/tools/bench_gen.js`，在 vm 沙盒里直接跑 `genLevel(lv)` 并读它记录的耗时/尝试次数。

**改前（1~40 关）**

| 指标 | 数值 |
|---|---|
| 合计 | **4022 ms** |
| 平均 | **100.5 ms / 关** |
| 最慢 | **219 ms**（第 18 关） |
| 单关最大尝试次数 | **202 次** |

关键发现：**`lv ≥ 16` 的关卡几乎每一次都跑满 200 次失败的 `solve()` 校验，才在第 200 次触发「加空管」兜底**（尝试次数停在 201~203 就是证据）。

原因是设计上的死结：`lv > 10` 的目标空管数是 1，而 **10 色 + 1 空管的随机填充几乎不可能通过可解性校验**——旧实现却在同一个空管数上死磕 200 次才肯加空管，而"加空管"本来就是必然要走的兜底路。**这 200 次 DFS 全部是纯浪费**（10 色一次失败校验约 1.7ms，200 次 ≈ 160ms；低端机按 10 倍算就是 1.5 秒的冻结）。

## 二、改法：分阶段尝试预算

```js
const GEN_STAGES = [40, 120, 400];   // 各阶段「累计尝试数」上限；空管数依次 base+0/+1/+2
const GEN_MASK_MS = 60;              // 上次生成超过该耗时，下次才先出遮罩让出主线程
const genStats = { tries: 0, ms: 0, empties: 0, colors: 0 };  // 诊断信息

function fillSolvable(colors, baseEmpties, rnd){
  const t0 = nowMs();
  let tries = 0, empties = baseEmpties, s = null;
  for(let st=0; st<GEN_STAGES.length && !s; st++){
    empties = baseEmpties + st;
    const cap = GEN_STAGES[st];
    while(tries < cap){ tries++; const cand = randomFill(colors, empties, rnd);
      if(solve(cand)){ s = cand; break; } }
  }
  ... // 极端兜底 + 写 genStats/genMsLast
}
function genLevel(lv){
  const colors = Math.min(2 + Math.floor((lv-1)/2), PALETTE.length);
  return {tubes: fillSolvable(colors, lv>10 ? 1 : 2)};
}
function genDaily(ds){ /* 同源 rnd 取色 → 复用 fillSolvable(colors, 2, rnd) */ }
```

即：**先用「更难」的目标空管数试一小段（40 次），不行再逐级加空管兜底**，总尝试硬上限 400。把原先 `genLevel` / `genDaily` 里两段几乎一样的循环抽成共用的 `fillSolvable()`。

**改后（1~40 关）**

| 指标 | 改前 | 改后 |
|---|---|---|
| 合计 | 4022 ms | **1090 ms** |
| 平均 | 100.5 ms/关 | **27.3 ms/关** |
| 最慢 | 219 ms | **88 ms** |
| 单关最大尝试次数 | 202 | **41** |
| 触顶(≥400)关卡数 | — | **0** |
| 保持目标空管数（难度未被拉平） | 由 200 次上限随机决定 | **16 / 40** |

最后一行值得说明：**难度没有为了提速被一刀切**。旧实现是"1 空管死磕 200 次 → 随机决定这一关到底是 1 空管还是 2 空管"，本身就是噪声；现在 40 次内能找到 1 空管解的就保持 1 空管，一共 16/40 关仍是"更难"的那一档。

## 三、配套：自适应遮罩（并把一个 backlog 项判定为「不该做」）

生成变快带出一个新问题：**遮罩会「闪一下」**。旧流程是无条件 `showGenMask()` → `setTimeout(0)` → 生成 → `hideGenMask()`；耗时 170ms 时遮罩是有意义的，降到 20ms 后它只是一次刺眼的闪烁。

改为：

```js
const needMask = genMsLast > GEN_MASK_MS;   // 上次慢 → 这次才先出遮罩让出主线程
if(needMask) showGenMask(...);
if(needMask) setTimeout(build, 0); else build();   // 快则同步生成，全程无遮罩
```

`startLevel` 与 `startDaily` 用同一套逻辑。快机器上**全程不出现遮罩**；慢机器上第一次慢生成之后，`genMsLast` 就会超过阈值，后续自动回到"先出遮罩再算"的降级路径。

同时把 backlog 里两项**判定为不该做并标记完成**（而不是留着当"永远修不完的待办"）：

- 「遮罩加**跳过**按钮」——遮罩期间是**同步阻塞**，主线程被生成占住，按钮根本点不动，这个修复无法生效；
- 「遮罩在无 rAF 环境降级为同步生成」——新逻辑本来就在快路径上同步生成。

## 四、一个必须守住的约束：预算不能按「墙钟时间」

分阶段预算有两种写法：累计尝试次数，或累计耗时。**只能选前者。**

因为每日谜题的"全服同一题面"依赖于**生成过程对所有设备完全一致**：日期种子决定随机序列，尝试次数决定停在哪一次。如果按耗时切换阶段，快机器会停在 stage 0、慢机器会切到 stage 1，**同一天的题面在不同手机上就不一样了**。

这条已写成断言（`GEN BUDGET` 段落里禁止生成预算里出现墙钟时间比较），避免以后有人"顺手优化"成时间预算。

## 五、启动顺序修正

`startLevel` 现在可能是**同步**的，而原先 boot 里的顺序是 `startLevel()` → `resize()`——同步路径下 `build()` 里的 `layout()` 会拿到 `W=0 / H=0`（`perRow` 算出 `NaN`，`tubeRects` 全是 `NaN`，只靠随后的 `resize()` 再 `layout()` 一次覆盖回来）。虽然最终状态正确，但会白跑一帧坏数据。已改为**先 `resize()` 再 `startLevel()`**。

本轮新增/加强的断言：
- 1~40 关逐关：**可解**（仍用 `solve()` 精确复验，没有改成"相信构造"）、管数合理、**尝试次数 < 400**（预算保护真的生效，而不是靠运气）；
- **禁止生成预算里混入墙钟时间比较**（守住每日同题面）；
- 自适应遮罩双向验证：`genMsLast=0` → `startLevel(5)` **不 drain 就已生成且遮罩未弹**；`genMsLast=999` → 先弹遮罩、`drain()` 后落地并隐藏；
- 每日谜题：可解 + 尝试次数不触顶 + **预告色数 === 实际色数**；
- `genMsLast` 与 `genStats.ms` 同步（否则自适应判断会永久失准）。

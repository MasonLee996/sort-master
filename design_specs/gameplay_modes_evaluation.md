# 评估：引入新玩法机制（限时模式 / 道具模式 / 其他）

> 状态：**待决策**。回答"玩法上能否引入新机制"，并给出成本、风险、约束边界的评估。
> 关联：`limit_step_and_difficulty_proposal.md`（难度天花板实测）、`progression_and_economy_review.md`（第 102 轮评审）。

---

## 0. 结论先行

**可以引入，但要先分清它们在解决哪个问题** —— 新玩法救不了"第 17 关难度躺平"，却正好能救"第 10 关撞顶之后"。这两件事不同轴：

| 问题 | 该用什么解 | 新玩法模式能否解决 |
|---|---|---|
| 主线难度在第 10 关撞天花板 | 新难度维度（CAP / 标注管） | ❌ 不能 |
| 第 10 关之后"没地方去"、没有长期目标 | 新**模式**（无尽 / 限时 / 周挑战） | ✅ 能 |
| 内容单一、玩家会腻 | 模式 + 规则变体 | ✅ 能 |
| 缺少"紧张感 / 挑战感" | 限时模式 | ✅ 能，且只有它能 |

**三条最重要的判断**：

1. **限时模式是唯一"无限可分"的难度轴** —— 时间是连续量，不消耗色数/空管/CAP 那点有限预算。这是我们前面算出"18 倍预算、9 关耗尽"之后，唯一能持续加压的维度。
2. **"硬性失败"应该放进可选模式，而不是塞进主线** —— 你之前想要"压力"，但主线是休闲向、无体力系统，失败态会劝退。限时模式是**独立入口**，可以真判负，主线继续保持"力竭不判负"。两边诉求同时满足。
3. **"道具模式"是个伪需求，需要拆成三种东西**（见 §3）。其中两种已经有了，第三种不建议做。

## 1. 限时模式：为什么它是钥匙

### 1.1 它绕开了难度天花板

| 难度轴 | 可分档数 | 上限 |
|---|---|---|
| 色数 | 9 档（2→10） | 第 17 关耗尽 |
| 空管 | 1 档（2→1） | 第 9 关失效 |
| CAP | 2~3 档（4→5→6） | 有限 |
| **时间** | **无限（连续）** | **无** |

时间可以 60s → 45s → 30s → 20s → 15s 一路细分下去，而且每一档都是玩家**立刻能感知**的难度提升。
其余旋钮是"离散且会耗尽"的，只有时间是"连续且不耗尽"的。

### 1.2 成本极低（可直接复用现有代码）

| 要做的事 | 复用 |
|---|---|
| 倒计时状态 + 每帧递减 | 现有 `rAF` 循环（`startPulse`/动画已在跑） |
| HUD 显示剩余时间 | 复用「步数」槽的写法（限时模式里限步为 0，两者不并存） |
| 看广告 +15 秒 | **复用「+5 步」那套**：同一个 `usedAdBoost` 计数、同一个每关 ≤2 次上限 |
| 失败弹窗 | 复用 `deadOverlay` 的结构，改文案与按钮 |
| 零新美术 | 进度条 = 一个 `fillRect`；不引入任何资源 |

**估算：一个模式 ≈ 现有"每日谜题"模式的三分之一工作量**（每日谜题已经趟平了"独立模式"该有的所有坑：独立 HUD、独立存档、独立胜负、入口路由）。

### 1.3 必须处理的四个边界（不做就是事故）

| # | 边界 | 后果 |
|---|---|---|
| 1 | **切后台/来电** → 必须 `visibilitychange` 暂停计时 | 玩家回来发现已经输了 → 差评 |
| 2 | **同一关只允许一种压力机制**（限步 XOR 限时，禁止并存） | 两个倒计时同时存在，玩家不知道该看哪个 |
| 3 | 低端机性能差异 | 只做**本机个人最佳**，不做"全服计时排行"（每日谜题保持只比步数） |
| 4 | 暂停/退出后是否保留进度 | 中途退出应当作放弃，但要有明确提示 |

### 1.4 定位建议

**不进主线，做成两个入口**：
- **限时挑战**：侧栏独立入口，按难度档位（轻松 60s / 标准 45s / 硬核 30s）自选，真判负，记录个人最佳。
- **每日限时**：与现有每日谜题**共用同一题面**，但计的是时间。因为题面已"全服一致"，只比时间也不涉及设备公平争议（只比本机最佳）。

## 2. 其余值得做的模式

| 模式 | 一句话 | 成本 | 为什么值得 |
|---|---|---|---|
| **无尽模式** | 连续过关，难度缓慢上升，步数/时间耗尽即结束，计分 | 中 | 第 10 关"毕业"后有地方去；天然承接限时/限步两种压力 |
| **周挑战** | 按**周**取种子的固定题面 + **一条规则变体**（如"本周禁用提示"/"本周只有 1 个空管"） | **低** | `hashSeed` + `mulberry32` 现成，改个种子前缀即可；规则变体只是几个开关 |
| **同题 PK 分享榜** | 本地记录 + 分享文案"这题我 34 步，你呢？" | **低** | 分享链路与文案已有，零后端 |
| **步数极限 / 金牌** | 用 ≤ 最优步数过关给额外奖励 | 低~中 | 已有 `refSteps`；真正的"最优"需 BFS（高关成本高）→ 可先用 `refSteps` 近似 |

**规则变体（Mutator）是被低估的一项**：它不改引擎、只改参数或开关，却能低成本提供"每天/每周不一样"的新鲜感。建议直接并入「周挑战」。

## 3. "道具模式"辨析：这是一个词指了三件事

| 类型 | 是什么 | 现状 | 建议 |
|---|---|---|---|
| **(a) 局内便利道具** | 提示券 / 撤销券 / 加管 / 护星徽章 | **已经有了**（商城 + 死局出口） | 不需要新"模式"，需要的是**把它们做好用** |
| **(b) 盘面机制 / 障碍** | 标注管、变容管、冰封球 | 未实现（已在难度提案中） | 这是**难度轴**，不是"道具模式" |
| **(c) 随机关卡道具玩法** | 每关发随机道具、用道具拼过 | 无 | ❌ **不建议**：会削弱解谜核心，且与 (a) 的概念混淆，玩家分不清"道具是买来的还是关卡给的" |

**如果要"道具感"，正确做法是把 (b) 做好**：标注管/变容管本身就是"盘面道具"，视觉上就能被理解为"这个抽屉有标签"。

### 3.1 红线（合规）

- ❌ 禁止**抽奖 / 开箱式**发放道具（已写入项目合规边界）
- ❌ 无版号期间**禁止任何真实付费**买道具或买时间
- ✅ 道具只走**金币兑换**或**看广告**
- ⚠️ 任何"加管/加步/加时"类便利道具，必须**显式告知对星级的影响**（现有 `assistNote` 口径要同步扩展）

## 4. 硬约束：模式不能无限加

本项目是**单文件 + 零外部资源 + 单指点击**，每加一个模式都要付固定成本：入口 → 弹窗 → 存档字段 → `layout()` 安全区 → 验证断言。

| 约束 | 上限 | 理由 |
|---|---|---|
| 侧栏入口总数 | **≤ 8** | 现有 `RAIL_ITEMS` 已 8 项（签到/每日/分享/排行/商城/首充/月卡/去广告），340px 窄屏滑动已经很满 |
| 同时存在的模式 | **≤ 4** | 闯关 / 每日 / 限时 / 无尽 |
| 同一关的压力机制 | **= 1** | 限步 XOR 限时 XOR 死局，禁止叠加 |
| 新增 UI 覆盖画布 | 必须预留 `layout()` 安全区 | 否则压住管子（项目既有铁律） |

→ **建议：新增模式必须"复用"而不是"新增"入口**。例如限时挑战与每日谜题可以合并进同一个 `dailyOverlay`（加一个"标准/限时"切换），而不是再挤一个入口进去。

## 5. 建议路线图

### 第一批（低风险、能直接解决当前两个卡点）

1. **标注管**（难度轴，解决"第 10 关撞顶"）—— 见难度提案 §3.3
2. **限时挑战**（压力轴，解决"没有紧张感" + 提供无限难度细分）
3. **无尽模式**（解决"毕业后无处可去"）
4. **周挑战 + 规则变体**（低成本内容多样性，复用日期种子）

### 第二批（看第一批数据再定）

5. 同题 PK 分享榜（复用分享文案）
6. 步数极限 / 金牌（需先决定用 `refSteps` 近似还是上 BFS）
7. 变容管（备选难度轴）

### 明确不做

- 冰封球（求解器状态空间爆炸，`key()`/记忆化全要重写）
- 三消 / 物理类新玩法（偏离收纳主题、违背单文件轻量）
- 随机关卡道具玩法（削弱解谜核心）
- 任何需要服务端的实时 PvP / 全服排行榜（违背"零依赖单文件"）

## 7. 验收要求（沿用项目既有规约）

1. `verify.js` 断言数**只增不减**（当前 269）。新增：
   - 限时：倒计时递减、归零判负、**`visibilitychange` 期间不计时**、广告加时上限、限时与限步**不并存**
   - 入口：新增/合并入口后 340px 窄屏 `layout()` 仍不压住管子（多尺寸渲染回归）
   - 存档：新模式字段在**所有** `start*` 入口正确归零（历史踩坑：`addedTubes`/`shielded` 都漏过一次）
2. **零外部资源**不破：计时条用 Canvas 绘制，不引任何图片/字体
3. 通关/失败文案与实得结果一致（表驱动断言，见难度提案 §5）

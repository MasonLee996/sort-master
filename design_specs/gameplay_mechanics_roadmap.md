## 2. 「破圈」怎么落到机制上

### 2.1 先明确一个前置判断

**Web 版可以立刻传播，微信小游戏版不行。**

| 发行路径 | 前置条件 | 现状 |
|---|---|---|
| **Web（GitHub Pages 链接）** | **无**（不是小游戏平台，无需版号/资质） | ✅ **已经上线，可立即传播** |
| 微信小游戏 | 企业/个体户主体 + 软著 + **版号** + 实名防沉迷 | ❌ 全部未办，周期长 |

→ **破圈的第一步应该走 Web**：分享链接 + 自绘二维码进海报。
→ 主体资质与版号应**尽早启动办理**（周期以月计），否则机制做得再好也上不了小游戏平台。这是**非代码**的并行任务。

### 2.2 四个机制各承担什么

| 机制 | 在"破圈"里承担 | 为什么有效 |
|---|---|---|
| **限时挑战** | **可炫耀的硬指标** | "30 秒过 10 色"是能截图、能发短视频的具体成就，比"我很厉害"可传播 |
| **同题 PK 分享榜** | **裂变引擎** | 每日题面已"全服一致"，"这题我 34 步，你呢？"是零成本、零后端的社交货币 |
| **标注管** | **差异化记忆点** | 竞品（经典 ball sort）没有"带标签的抽屉"，这是玩法的**辨识度** |
| **无尽模式** | **长期留存** | 给"通关之后"一个分数目标，把一次性体验变成可反复挑战的对象 |
| **周挑战 + 规则变体** | **低成本新鲜感** | 复用日期种子，每周换一条规则，几乎零增量成本 |

### 2.3 一句话判断

**难度曲线决定"能不能玩得下去"，玩法机制决定"能不能被传播"。** 两者都要，但顺序上先做完难度（P1–P4），再做传播型机制（P5–P6）。

## 3. 分期计划（逐步完成）

> 每期都是「工程师实现 → QA 独立验证 → team-lead 验收」，
> **`verify.js` 断言数只增不减**（当前 269），每期结束必须跑通 + 推送 + 线上逐字节核验。

### P1 · 限步「力竭」+ 4 个缺陷修复（D1–D4）—— ✅ **已完成**

> 交付结果：`verify.js` **PASS=409 / FAIL=0**（起点 269 → 工程师 319 → QA 365 → 第二轮 409）；
> `bench_gen.js` 独立复测 3 次，中位数平均 27.1ms / 最慢 63ms，**无退化**；7 条铁律经 `git show HEAD` 逐字节比对**零改动**。
> 落地过程中额外发现并修掉一个**经济漏洞**（见下表最后一行）。

| 项 | 位置 | 做法 |
|---|---|---|
| 力竭拦截 | `onTap()` L973 `if(canPour(...))` 分支内、`pushHistory()` **之前** | `if(moveLimit>0 && moves>=moveLimit && !isWin(tubes)){ showExhausted(); return; }` |
| 弹窗 | 仿 `deadOverlay`（HTML L148） | 新增 `exhaustedOverlay`：看广告 +5 步（剩 N 次）/ 金币 40 换 5 步 / 重开本关 |
| 广告加步上限 | `btnAd` L1199 | 新增单关计数 `adStepsUsed`，**每关 ≤2 次**；`noAds` 用户直接发放不播广告 |
| 重开同一题面 | `btnRestart` L1198 | 缓存当前题面（`tubes/refSteps/baseTubes`），重开=重置状态而非重新生成 |
| 评级三处同步 | `calcStars()` L1082 / `assistNote()` L1093 / help 规则 L135-139 | 加步计入辅助 → 上限 ★★；`shielded` 可免 |
| **通关奖励幂等化**（新发现的经济漏洞） | `win()` L1120-1155 | 现在 `coins += 10 + st*5` **无条件发放** → 反复重玩同一关即可无限刷金币，会直接冲垮刚建立的商城经济。改为：**首次通关发全额；重复通关只发"星级提升的差额"**（`max(0, 新星 - 历史最佳) × 5`）；每日谜题已有幂等（`dailyDoneDate`），保持不动 |

**验收**：力竭时合法落子被拦；`isWin` 优先放行；第 3 次广告加步被拒；`noAds` 免费加步；重开前后 `tubes`/`refSteps` 一致；表驱动断言扩到含 `adStepsUsed` 的 16 条路径；**同一关连续通关两次，第二次金币不增加（星级提升除外）**。

### P2 · 难度曲线第一阶段（D5/D8/D10/D11/D12）

- 抽出 **`LEVEL_CURVE` 表**（关卡 → 色数/空管/CAP/标注管数），`genLevel` 只读它（**单一出口**）
- 空管**确定性锁死**（修缺陷 D）；`fillSolvable` 兜底上限收紧为"最多 +1"
- **第 1 关手工写死教程关**（固定题面、≤3 步、重开同题面）
- 第 2–9 关每关 +1 色（把 16 关爬坡压到 9 关）
- 补 `genStats.dfsNodes`（求解器回溯次数）作为难度度量

**验收**：1~50 关生成参数与表一致（大样本，非"连跑几次"）；第 1 关题面固定；难度单调不回退。

### P3 · CAP 可变 + 分章体量（D5 后半）

- `CAP` 由顶层 `const` 改为 `capOf(level)`，改全部引用（`randomFill`/`canPour`/`pour`/`moveCount`/`isWin`/`render`/`layout`）
- L10 起 CAP=5（×1.42）、L13 起 CAP=6（×1.21）
- `bench_gen.js` 复测（10 色 50/60 球的 DFS 成本）

**验收**：CAP 变更后球数仍恒为 `colors×CAP`；生成耗时无可见退化（须独立复测）。

### P4 · 标注管（D6，难度天花板的正解）

- `solve()` 增加返回 `final`（解终态）
- `canPour()` 加标注约束：`if(label[j]!=null && a[a.length-1]!==label[j]) return false;`
- 生成时**把"该管在解里最终装的颜色"贴上去** → **不破坏可解性**
- 渲染贴色标（零外部资源，Canvas 绘制）
- L17 起 1 根，每 10 关 +1，上限 3 根

**验收**：标注约束下原解路径仍合法（**可解性不变量**）；标注数随关卡递增；第 4 条铁律（`isWin` 口径等）不变。

### P5 · 限时挑战（D13–D15、D18）

- 独立模式 + 独立 HUD（限时模式里限步为 0，两者**不并存**）
- `visibilitychange` **暂停计时**（切后台不算失败）
- 看广告 +15 秒（复用 P1 的 `adStepsUsed` 计数与每关上限）
- 与每日谜题**共用入口**（加「标准 / 限时」切换）
- 真判负 + 本机个人最佳（**不做全服计时排行**）

**验收**：倒计时递减、归零判负、切后台不计时、加时上限、限时与限步不同时激活。

### P6 · 无尽模式 + 周挑战（D16/D17、D7）

- 无尽：连续过关、难度缓慢递增、步数/时间耗尽即结束、计分
- 周挑战：`hashSeed` 换周种子 + **一条规则变体**（禁用提示 / 只有 1 个空管 / 限时等）
- 章节 + 集星（每章 10 关 / 30 星）—— 让"第 10 关毕业"后有可见进度

**验收**：模式切换时新增单关状态量在**所有** `start*` 入口归零（历史踩坑：`addedTubes`/`shielded` 都漏过一次）。

## 4. 红线（不因新机制而破）

| 红线 | 说明 |
|---|---|
| **零外部资源** | 所有新 UI（倒计时条、色标）必须 Canvas 程序化绘制，不引任何图片/字体/CDN |

| **合规** | 无版号期间禁止任何真实付费；禁止抽奖/开箱式发放；道具只走金币兑换或看广告 |

### 3.1 P1 的落地明细与教训（供后续各期复用）

**改了什么**（`index.html` +151 / −24）：

**三条教训（已同时写入项目记忆）**：
- **「重开」入口不止一个**：底栏 / 死局弹窗 / 力竭弹窗 / 胜利重玩共 **4 个**，改重开口径时必须全覆盖 —— 本轮只改了 2 个，被 team-lead 查出 `btnDeadRestart` 仍在重掷新题（且每日模式里会把玩家踢出 daily）。
- **复制逻辑必然分叉**：`doUndoExhausted()` 是 `doUndo()` 的复制版，QA 逐行对照确认等价（含**撤销券优先消耗**分支与动画守卫）。后续凡"对齐某函数"的需求，都要让 QA 逐行 diff，而不是接受"完全对齐"的声明。
- **断言只增不减要防"被收买"**：本轮工程师改写了 QA 的 2 条断言（预期值随设计变更而更新）。QA 复核判定为**合法预期更新、非强度削弱**。凡有断言被改写，都必须由**写它的人**复核强度是否被削弱。
